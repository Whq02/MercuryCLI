# Mercury CLI

Mercury CLI (mercury-cli.ai, npm-пакет `mercury-tech-cli`) запускает ИИ-агентов для написания кода в вашем терминале, внутри ваших git-репозиториев на macOS, Linux и Windows.

Сайт: [mercury-cli.ai](https://mercury-cli.ai) · Репозиторий: [github.com/Whq02/MercuryCLI](https://github.com/Whq02/MercuryCLI) (`Whq02/MercuryCLI`) · npm: `mercury-tech-cli`

Агент читает и редактирует файлы, выполняет shell-команды, пошагово проходит тесты и отладчики и проверяет результаты. Вы выбираете провайдера моделей, саму модель и то, что агенту разрешено делать:

- **Несколько сессий в Concourse и изолированные worktrees:** запускайте несколько сессий бок о бок в Session Concourse (`/concourse`) и передавайте параллельную работу crewmates (напарникам, `Crewmate`) от разных провайдеров в изолированных рабочих копиях `git worktree` с арендой файлов проекта, чтобы параллельные агенты не перезаписывали работу друг друга.
- **22 провайдеров моделей, `/llmhost` и `/localsetup`:** держите все 22 провайдеров подключёнными одновременно (OpenAI, Anthropic, Google Gemini, DeepSeek, Moonshot/Kimi, Z.AI/GLM, OpenRouter, Hugging Face, xAI/Grok, Meta/Muse, Mistral, Nous Portal, OpenCode Zen, Qwen, MiniMax, Together AI, Cohere, Groq, Cerebras, Fireworks AI, Melious AI, OrcaRouter) и переключайте провайдеров и модели прямо в чате. Откройте `/llmhost`, чтобы выбрать модель, проверить её квантизацию, разбиение `conversations × context` и уровень размышлений, а также запустить её на арендованном GPU (Runpod, Vast.ai или Lambda), на своём компьютере (`mercury host`) или на существующем сервере. Или выполните `/localsetup`, чтобы установить или подключить Ollama вместе с LM Studio, vLLM и llama.cpp.
- **Гибридная RAG-память проекта Mneme:** использует работающую на устройстве семантическую модель эмбеддингов BGE на 118 МБ (`bge-base-en-v1.5`), ранжирование слов по BM25, отслеживание цитат, закреплённые правила дословно, стартовый контекст с учётом ветки, проверки противоречий при записи, заметки о передаче между сессиями и граф в браузере, открываемый командой `/memory page`.
- **Инструменты компилятора, AST и отладки DAP:** подключает LSP-анализ кода и рефакторинги с предварительным просмотром (`LspRead`, `LspRename`, `LspMoveSymbol`, `LspMoveFile`, `LspCodeAction`, `LspFormat`), структурный поиск и переписывание по AST tree-sitter для 23 языков (`AstSearch`, `AstEdit`), встроенный отладчик по Debug Adapter Protocol (`Debug`) с адаптерами (`debugpy`, `js-debug`, `lldb`, `gdb`, `dlv`) для пошагового входа в падающие тесты на Python, Node, Go и Rust, а также постоянные ячейки `Eval` на Python и JavaScript.
- **`WebSearch` без ключей и `WebFetch` в markdown:** ищет через собственный поиск провайдера, через ключи Brave или Tavily, официальные API (Stack Exchange, npm, PyPI, crates.io, GitHub, Hacker News, Wikipedia), SearXNG и DuckDuckGo без ключа, а также загружает публичную документацию в markdown в пределах бюджета вызова 38 000 символов.
- **Управление компьютером на рабочем столе, голосовой ввод Whisper, планирование Saturn и мосты к редакторам:** управляет приложениями рабочего стола (`Computer`), расшифровывает голосовую диктовку push-to-talk на устройстве с помощью Whisper (`/voice`), планирует повторяющиеся или разовые сессии через Saturn (`/saturn`) и подключается к VS Code по Agent Client Protocol (`mercury acp`) вместе с Unity, Blender, Godot и Aseprite.
- **Генерация видео (`Video`):** передавайте промпты и справочные файлы проекта настроенному генератору MiniMax ([docs/VIDEO.md](../VIDEO.md)) и сохраняйте созданный MP4 и необязательный PNG-кадр предпросмотра на 1-й секунде в вашем проекте.

Mercury используется для разработки самого Mercury: несколько сессий и моделей работают над долгими задачами. Труднее всего отслеживать эту работу: что ещё выполняется, что изменилось и что требует решения. Каждая сессия при завершении пишет собственную заметку о передаче, а следующая читает её один раз при запуске вместе с моими закреплёнными правилами, и это предотвращает отравление контекста между сессиями.

Mercury распространяется с открытым исходным кодом по лицензии Apache License 2.0, как и SDK в [sdk/](../../sdk/) и [sdk-py/](../../sdk-py/).

## Установка

Архивы релизов доступны для Mac на Apple silicon и Intel, Linux x64 и arm64, а также Windows x64 и arm64. Установите `git` отдельно: каждый архив включает Node и ripgrep, поэтому отдельная установка Node не нужна.

Выберите один способ установки:

```sh
curl -fsSL https://mercury-cli.ai/install | sh     # macOS и Linux (x64 и arm64)
irm https://mercury-cli.ai/install.ps1 | iex        # Windows (x64 и arm64), в PowerShell 7
brew install Whq02/mercury/mercury                 # Homebrew: macOS и Linux x64
npm install -g mercury-tech-cli                    # npm; `bun install -g mercury-tech-cli` — тот же пакет
mise use -g npm:mercury-tech-cli                   # mise, через пакет npm
```

Адреса установки ведут приблизительный подсчёт запросов скриптов по источникам и дням UTC (завершённые установки не учитываются); счётчик не хранит IP-адрес, строку user-agent или cookie.

Откройте новый терминал или выполните строку `export PATH=…`, которую выводит установщик для shell, затем проверьте установку командой `mercury --version` и запустите `mercury` из репозитория, чтобы начать [первый запуск](#первый-запуск). В PowerShell в Windows, а также после установки через Homebrew, npm, bun или mise команда `mercury` работает в том же терминале.

### Чем отличаются способы установки

Установщики для shell и PowerShell загружают новейший релиз для вашей платформы, проверяют его SHA-256 по `SHA256SUMS.txt`, распаковывают его и запускают собственную команду архива `mercury install`.

И формула Homebrew, и npm-пакет привязаны к конкретному релизу и публикуются заново после тега, поэтому могут отставать от самого нового релиза. Команды Homebrew используют полное имя tap `Whq02/mercury/mercury` (просто `mercury` в `homebrew-core` — другая программа). npm-пакет `mercury-tech-cli` — лаунчер, который загружает закреплённый за ним релиз; mise устанавливает тот же пакет. `mercury install --uninstall` удаляет установленный релиз и командный шим, сохраняя вашу конфигурацию и сессии (если вы устанавливали npm-лаунчер, выполните также `npm uninstall -g mercury-tech-cli`).

Установка Mercury выполняется в каталоге пользователя и не требует прав администратора. Команду установки можно безопасно запускать повторно.

### Пути установки

Версии релизов хранятся в каталоге конфигурации по пути `~/.mercury/versions/<version>` (на Windows — `%USERPROFILE%\.mercury\versions`). Команда `mercury` устанавливается в `~/.local/bin` на macOS и Linux или в `%LOCALAPPDATA%\Mercury\bin` на Windows.

`mercury install` один раз добавляет каталог команды в PATH: защищённая строка в файле запуска shell или запись в пользовательский PATH Windows. Новый терминал подхватывает изменение автоматически.

### Обновления

Используйте `mercury update` с любым способом установки.

Для установки через установщик shell или PowerShell либо через `mercury install` команда обновляет Mercury на месте. `--check` проверяет наличие обновлений, `--status` показывает статус обновления, а `--rollback` возвращает предыдущую версию, которая остаётся на диске.

Для Homebrew команда запрашивает подтверждение перед запуском `brew upgrade Whq02/mercury/mercury`. По умолчанию ответ — «нет»; введите `y`, чтобы подтвердить. Mercury выводит результаты команды по мере их поступления и проверяет установленную версию после её завершения. Используйте `--yes`, чтобы пропустить запрос в скриптах.

npm-лаунчер использует ту же структуру релизов, что и установщики, и передаёт каждый запуск установленному релизу. Поэтому `mercury update` обновляет npm-установку на месте через собственный канал обновлений Mercury. `npm update -g mercury-tech-cli` меняет только релиз, который пакет установит при первом запуске. Это относится и к mise.

`--check` читает один и тот же список релизов для каждого способа установки и сообщает, как обновить вашу установку. Когда доступно обновление, на домашнем экране один раз в правом нижнем углу выводится `vX.Y.Z available · mercury update`, а в чате то же уведомление остаётся до обновления. Чтобы скрыть оба, задайте `MERCURY_UPDATE_NOTICE=0`.

Запросы установки и обновления анонимно загружают публичный список релизов и архивы; их можно выполнять без учётной записи и токена. Если анонимный запрос отклонён, Mercury обращается к вошедшему в аккаунт GitHub CLI (`gh`).

После обновления Mercury проверяет, указывает ли команда в вашем PATH на обновлённую установку. Если приоритет имеет другая установка или обновлённая команда отсутствует в PATH, Mercury объясняет проблему и способ её исправить. `mercury health` сообщает о той же проблеме.

### Проверка релиза

Перед активацией релиза Mercury проверяет его архив по `SHA256SUMS.txt`. Также он требует, чтобы полезная нагрузка была подписана ключом релиза Mercury из встроенного в программу списка доверенных ключей, прежде чем подготовить обновление. Отклонённая подпись оставляет действующую установку без изменений.

Используйте `--allow-unsigned`, чтобы принять неподписанную полезную нагрузку. Mercury всё равно отклоняет неизвестные ключи подписи, повреждённые блоки подписи и подменённое содержимое. Результат команды и её локальная запись показывают, что вы разрешили неподписанную полезную нагрузку.

Архивы выпусков подписаны. Выполните `mercury health`, чтобы проверить подпись установленного выпуска.

Архив без подписи выпуска помечается как неподписанный. Установка и обновление отклоняют его, если не указать `--allow-unsigned`.

[docs/TRUST.md](../TRUST.md) объясняет результаты проверки и то, как проверить архив вручную. [docs/TERMINAL-RUNTIME.md](../TERMINAL-RUNTIME.md) описывает проверку при запуске.

## Требования

Архивы релизов включают Node 24 LTS. Лаунчер, `mercury install` и `mercury update` используют этот встроенный runtime; `git` — единственное отдельное требование для самого релиза.

Для сборки из исходного кода нужно:

- **Node 24 LTS** в поддерживаемом диапазоне `>=24.20.0 <25`. `.node-version` фиксирует патч-версию, которая используется для сборок и входит в архивы релизов.
- **bun 1.3.x** для сборки. В релизы он не входит.
- **git**. В Windows запускайте PowerShell 7 внутри Windows Terminal или терминала VS Code. См. [docs/INSTALL-WINDOWS-FROM-SOURCE.md](../INSTALL-WINDOWS-FROM-SOURCE.md).

Минимальная версия Node включает исправление nodejs/node#56645. Ниже 24.20.0 headless-команды `run`, которые вызывают инструмент, аварийно завершаются при выходе в Windows.

Лаунчеры выбирают Node в таком порядке: явный бинарный файл `MERCURY_NODE`, встроенный runtime, затем совместимая установка Node в PATH. Если runtime отсутствует, лаунчер выводит ошибку.

### Shell в Windows

Архивы релизов включают bash-совместимый движок shell Mercury (`brush`). В Windows он по умолчанию обслуживает инструмент Bash: находит программу `.cmd` или `.bat`, например `npm`, по имени без расширения через PATHEXT, передаёт `%VAR%` и `^` пакетному файлу без изменений, запускает программу, заданную относительным путём, после `cd` и сохраняет состояние shell между вызовами. Git for Windows `bash.exe` не нужен; если он установлен, `MERCURY_SHELL_ENGINE=system` или значение `system` в `/config` в настройке Shell engine запускает инструмент Bash только через `bash.exe`.

Посмотрите строку `shell` в проверке состояния, чтобы узнать, какая оболочка активна и почему: встроенный движок (по умолчанию в Windows или если его включили закреплением или настройкой) либо Git Bash, если движок выключен или его пакет отсутствует.

В macOS и Linux по умолчанию используется системный shell. Чтобы выполнять инструмент Bash и там на встроенном движке с сохранением состояния shell, задайте `MERCURY_SHELL_ENGINE=brush` или выберите `brush` в `/config` в настройке Shell engine.

Сборка из исходников без пакета движка или Git for Windows всё равно запускается, но инструмент Bash недоступен. Инструмент PowerShell остаётся доступен, а диагностика `shell` объясняет, как вернуть поддержку Bash.

## Сборка из исходного кода

Mercury собирается с bun и работает на Node 24 LTS. Установите [требования к сборке из исходников](#требования), включая bun 1.3.x:

```sh
curl -fsSL https://bun.sh/install | bash           # macOS и Linux
powershell -c "irm bun.sh/install.ps1 | iex"       # Windows, в PowerShell 7
bun --version                                      # 1.3.x
```

Затем в клоне этого репозитория:

```sh
bun run setup                      # один раз; bun install + вендорные пакеты
bun run build.ts                   # записывает dist/mercury.mjs + dist/manifest.json
node dist/mercury.mjs --version
node dist/mercury.mjs
node dist/mercury.mjs health --json
```

### Поддержка терминала

Полноэкранному интерфейсу нужен настоящий TTY, но минимального размера терминала нет. Полная раскладка начинается от 100 столбцов на 26 строк; окна меньшего размера используют компактную раскладку.

Mercury использует 24-битный цвет, если терминал сообщает о поддержке через `COLORTERM=truecolor` или распознаётся как iTerm2, Ghostty, WezTerm, Kitty, Windows Terminal или VS Code. Другие терминалы используют 256 цветов, включая Terminal от Apple в macOS 15 и более ранних версиях.

Строка Terminal color в проверке состояния показывает определённую глубину цвета и причину. Задайте `MERCURY_TRUECOLOR=1` для терминала, который поддерживает истинный цвет, но не сообщает об этом, или `MERCURY_TRUECOLOR=0`, чтобы принудительно использовать 256 цветов.

### Дополнительные компоненты

`setup` загружает встроенные пакеты возможностей: pyright, debugpy, js-debug, дополнительные грамматики, Node runtime для платформы и brush. Если загрузка не удалась, этот пакет пропускается, а сборка и затронутые инструменты сообщают о недостающем компоненте. Команда `bun install` сама по себе даёт сборку без этих пакетов.

Чтобы собрать поддержку голоса, запустите `setup` с установленным Rust. Это собирает `native/voice`. Добавьте cmake, чтобы собрать также `native/whisper`. При установленном Rust `setup` также собирает аддон драйвера рабочего стола (`native/desktop`), через который работает инструмент `Computer`. При наличии Rust `setup` собирает и локальный аддон эмбеддингов (`native/embed`, `bun run scripts/vendor/build-embed.ts`) и загружает модель BGE на 118 МБ (`bun run scripts/vendor/fetch-embed-models.ts --default`); без cargo пакет пропускается, setup сообщает об этом, а поиск по памяти Mneme работает только по совпадению слов. Каждый архив релиза содержит пакет эмбеддингов, собранный для его платформы; в Linux и Windows вычисления выполняет векторизованное ядро, поэтому Recall по смыслу занимает около одной десятой секунды (несколько сотых на macOS, где используется Accelerate). Если в нативной сборке не хватает инструментов, setup её пропускает, а проверка состояния сообщает об отсутствующем аддоне. Движок shell для Windows тоже собирается на вашей машине, потому что в upstream нет бинарного файла для Windows.

См. [Shell в Windows](#shell-в-windows) и [docs/TERMINAL-RUNTIME.md](../TERMINAL-RUNTIME.md) о движке shell `brush`.

Сборка пишет только в `dist/`. Конфигурация и сессии хранятся в `~/.mercury` или в каталоге, заданном `MERCURY_CONFIG_DIR`, и создаются при первом запуске. В Windows запускайте `node dist\mercury.mjs` напрямую.

### Установка сборки из исходников как команды

`scripts/ops/deploy-runtime.sh` публикует сборку из чистого дерева в новую папку `<config home>/runtime/builds/<build>` и направляет на неё `runtime/current` (`runtime/dist` — более старое название той же ссылки). `scripts/ops/deploy-launcher.sh` устанавливает лаунчер в `<config home>/bin/mercury`. Добавьте этот каталог в PATH; для zsh:

```sh
echo 'export PATH="$HOME/.mercury/bin:$PATH"' >> ~/.zshrc
```

Лаунчер завершается с ошибкой, если runtime отсутствует. Он не переключается на другую сборку. Выбор Node следует порядку из раздела [Требования](#требования). Для установки релиза выполните `mercury install` или `mercury update`: они не меняют рабочие копии исходников; см. [Обновления](#обновления).

[AGENTS.md](../../AGENTS.md) — краткое руководство по сборке и запуску. [BUILD-NOTES.md](../../BUILD-NOTES.md) подробнее описывает сборку.

## Первый запуск

При первом интерактивном запуске выберите оформление, затем войдите в аккаунт провайдера. Экран показывает предпросмотр темы, пока вы её выбираете. По умолчанию выбрана тема True Black; остальные варианты — тема oasis dark и тема Black and white, которая не добавляет никакого цвета: используются собственные цвет текста и фон терминала, так Mercury выглядит в терминале без цвета. Позже это можно изменить командой `/appearance`.

Вы также можете выбрать «sign in later», чтобы осмотреться без подключения аккаунта. Если ключ провайдера в вашем окружении уже выполняет вход для провайдера, шаг входа не запрашивается. Затем шаг Guardrails напоминает проверять правки и команды Mercury, а также что прочитанное может содержать инструкции для модели. В терминале, который Mercury умеет настраивать (Terminal.app, семейство VS Code, Alacritty, Zed), шаг Terminal keys может настроить сочетания клавиш для новой строки в настройках самого терминала (в Terminal.app на macOS он назначает `Option+Enter` для новой строки и отключает звонок терминала во всех профилях, что вступает в силу после перезапуска Terminal.app; в семействе VS Code, Alacritty и Zed записывает `Shift+Enter` для новой строки). Он выключен, пока вы его не выберете, и резервная копия сохраняется.

Затем Mercury спрашивает, доверяете ли вы открытой папке. Ничего, что запрошено конфигурацией рабочего пространства, не выполняется до того, как вы предоставите это доверие. Доверие распространяется на весь репозиторий; отказ завершает работу Mercury. См. [docs/TRUST.md](../TRUST.md).

Обычный интерактивный запуск открывает домашний экран. В нём десять пунктов меню; пункт Continue Last Session появляется только после того, как у вас появится история сессий:

- **New Session in \<folder\>** запускает новую сессию в текущей папке.
- **Continue Last Session** возвращает к вашему последнему чату.
- **Boot Menu** настраивает будущие сессии, включая motion, crewmates и рабочие процессы.
- **MCPs & Skills** выбирает, что загрузит следующая сессия. См. [docs/KIT.md](../KIT.md).
- **Agents** создаёт и редактирует агентов.
- **Health Check** проверяет установку.
- **Saturn Scheduler** планирует сессии. См. [docs/SATURN.md](../SATURN.md).
- **Logins** подключает аккаунты провайдеров.
- **Session Concourse** открывает список сессий текущего проекта.
- **Sessions · Projects** позволяет выбрать сессию или репозиторий.

Пункты меню открываются поверх домашнего экрана, а `Esc` возвращает к выбранному пункту. Список сессий открывается на отдельном экране, его также можно открыть через `Shift+→`. Аргумент с prompt, `--continue` или `--resume` сразу открывает чат.

### Motion, crewmates и рабочие процессы

В разделе Performance меню Boot Menu есть настройка Motion: `auto`, `full`, `reduced` или `off`. Она управляет анимацией простоя в интерфейсе и доступна также в `/config`.

В разделе Agents переключатели Crewmates и Workflows определяют, получают ли новые сессии инструменты Crewmate и Workflow. Выключение переключателя убирает соответствующий инструмент; попытки запустить работу этого типа возвращают то же объяснение. В сессии `/crewmates on|off` и `/workflows on|off` меняют эту настройку со следующего хода.

## Ежедневный цикл работы: Session Concourse, git worktrees и crewmates

### Запуск сессии и изоляция worktrees

Нажмите `Enter` на пункте New Session, чтобы создать сессию в текущей папке с моделью по умолчанию. Mercury открывает чат и одновременно добавляет его в список сессий. За меню Mercury держит готовым процесс, чтобы сократить работу при запуске.

Запуск другой сессии не останавливает предыдущую: можно оставить задачу выполняться и работать в другом месте. Запустите с `--worktree [name]` (или попросите в чате `worktree`, чтобы выполнить `EnterWorktree`), чтобы сессия получила собственную ветку и рабочую копию в `.mercury/worktrees/`. Параллельные crewmates тоже могут работать в изолированных worktrees и согласовывать общие файлы через аренду файлов проекта; см. [Что внутри](#что-внутри-память-mneme-rag-lsp-ast-для-23-языков-отладчик-dap-веб-поиск-и-мосты) и [docs/CREW.md](../CREW.md).

### Работа в чате

Опишите задачу обычными словами. Агент читает, редактирует, запускает и проверяет код в рамках выбранного режима разрешений. Вызовы инструментов отображаются по мере выполнения — компактными карточками или с полным выводом. Вид выбирается в `/config` в разделе Tool output; настройка сохраняется для следующих запусков.

Используйте `/model` и `/effort`, чтобы настроить сессию. `/permissions` определяет, что может выполняться без подтверждения, а что требует спросить сначала.

Просматривайте изменения через `/diff` — по источнику, файлу и фрагменту (hunk). `! <command>` выполняет shell-команду прямо в чате с живым выводом последних строк. `/runs` показывает запущенные shell-процессы и crewmates (`/tasks` открывает ту же доску), а `/crewmates` открывает живой вид Crew. Между ходами `/clear` сохраняет текущий чат и открывает новую сессию, а `/restart` переносит чат на только что установленную сборку Mercury. `/title` даёт чату название, а `/help` выводит список доступных команд.

### Переход между экранами

`Shift+←` и `Shift+→` переключают между доступными сейчас экранами. При новом запуске доступны домашний экран и список сессий. Экран чата добавляется, когда сессия получает фокус, и убирается, когда закрывается последний чат. Подсказки клавиш показывают только доступные переходы.

Закрытие всех чатов возвращает вас на домашний экран. Используйте `--chat`, чтобы оставить только домашний экран и чат, без списка сессий. `--concourse-off` сохраняет этот выбор для будущих запусков; `--concourse-on` или `/config` включает его снова.

### Управление сессиями в Session Concourse

Откройте список сессий командой `/concourse` или через `Shift+→` с домашнего экрана. Сначала показываются запущенные сессии текущего проекта, затем сохранённые чаты, которые не запущены, — от самых новых к старым.

У каждой запущенной сессии есть ячейка NOW с её текущей активностью. Выберите строку и нажмите `Enter`, чтобы вернуться в чат, пока остальные сессии продолжают работать. Упавшая сессия остаётся в списке сессий как NEEDS YOU вместе с причиной, пока вы её не освободите.

[docs/SESSIONS.md](../SESSIONS.md) описывает жизненный цикл сессии.

## Провайдеры и модели: входы в аккаунты, `/localsetup` и `/llmhost`

Чтобы подключить провайдера, используйте `/logins`. Команда открывает тот же каталог входов, который используется при настройке. Подключёнными слотами провайдеров потом управляет `/accounts`.

- **OpenAI:** подписка ChatGPT или ключ API.
- **Anthropic:** подписка Claude, вход в Console или ключ API.
- **OpenRouter:** доступ к каталогу через OAuth или ключ API; запросы к моделям запрещают сбор данных и всегда требуют, чтобы провайдер поддерживал все параметры запроса. `/config → OpenRouter routing policy` задаёт варианты резервного маршрута и режима нулевого хранения данных; выберите open, чтобы ослабить политику и передать маршрутизацию OpenRouter.
- **Google Gemini:** Sign in with Google, ключ API или собственный клиент OAuth. Sign in with Google запускает Gemini за счёт квоты тарифа, который есть у аккаунта Google (бесплатный аккаунт, Google AI Pro или Google AI Ultra), через собственный клиент Antigravity от Google: промпт, схемы инструментов и результаты инструментов отправляются на эндпоинт Code Assist от Google под этим клиентом и вошедшим аккаунтом, а `/model` показывает список моделей, которые Google предоставляет аккаунту. Ключ API или собственный клиент OAuth вместо этого выставляют счёт проекту Cloud.
- **Hugging Face:** вход по коду устройства или токен Hub.
- **Kimi (Moonshot):** вход по коду устройства или ключ API.
- **GLM (Z.AI):** ключ подписки GLM Coding Plan или общий ключ API с оплатой по мере использования. `/logins zai` сохраняет любой из них и записывает тариф; `ZAI_API_KEY` тоже работает, а `ZAI_KEY_PLAN=coding|general` задаёт тариф (если не задано, Mercury читает его из списка моделей самого ключа).
- **DeepSeek:** ключ API из платформы DeepSeek (`/logins deepseek` или `DEEPSEEK_API_KEY`).
- **xAI (Grok):** войдите по своей подписке Grok (SuperGrok / X Premium) или вставьте ключ API через `/logins xai`.
- **Meta (Muse):** Sign in with Meta (подписка Muse Code, код устройства в браузере) или ключ Model API с оплатой по мере использования. Sign in with Meta обменивает код устройства через OIDC-эндпоинты Meta (`https://auth.meta.com/oidc/device/authorization/` и `/oidc/device/token/`) под публичным client id Muse Code, один раз отправляет полученный токен аккаунта на `https://api.meta.ai/muse-code/key`, чтобы выпустить API-ключ подписки (а также при ограниченных запросах `/usage` для уровня тарифа и окон использования), и на каждом запросе к модели отправляет на `https://api.meta.ai/v1` только выпущенный ключ. Вставленный ключ Model API или `MODEL_API_KEY` / `META_API_KEY` тарифицируется по мере использования.

- **Qwen:** ключ QwenCloud (тариф Token Plan или оплата по мере использования) или ключ Alibaba Cloud Model Studio (оплата по мере использования, Token Plan или Coding Plan), который проверяется на собственном эндпоинте до сохранения; ключ тарифа выводит модели этого тарифа, Qwen3.8 Max — первой.
- **MiniMax:** ключ Open Platform или ключ подписки M Plan.
- **Together AI** и **Cohere:** ключ API.
- **Groq**, **Cerebras** и **Fireworks AI:** ключ API; ключ любого семейства также может поступать из команды, заданной в `credentials.keyCommands.<family>`.

Mistral, Nous Portal и OpenCode Zen тоже подключаются через `/logins`: всего 22 семейств провайдеров с входом. Локальные серверы моделей (Ollama, LM Studio, vLLM и llama.cpp) и пользовательские конечные точки, совместимые с OpenAI, работают без входа провайдера. Выполните `/localsetup`, чтобы установить или запустить Ollama, загрузить модель, которая помещается в вашу память, задать окно контекста или подключить работающий сервер LM Studio, vLLM или llama.cpp ([docs/LOCAL-SETUP.md](../LOCAL-SETUP.md)). Каждый провайдер использует собственный протокол, учётные данные и обработку ошибок, а запросы никогда не переходят к другому провайдеру. См. [docs/ENGINES.md](../ENGINES.md).

`/llmhost` выводит список моделей, которые можно разместить, и показывает, где каждая из них может работать прямо сейчас: на GPU, арендованном у Runpod, Vast.ai или Lambda, на вашем компьютере или на сохранённом SSH-компьютере (`mercury host`), либо на существующем сервере моделей. На странице каждой модели показаны варианты квантизации, распределение памяти GPU между параллельными разговорами (`conversations × context`) и уровень размышлений по умолчанию (его для каждого запроса меняет `/effort`). Аренда GPU требует явного подтверждения почасовой цены, а настройка продолжается в фоне, если закрыть всплывающее окно. На Runpod можно также настраивать качество, разбиение контекста и размышления до аренды или на уже запущенном поде (`Tune`), держать веса на томе с быстрой загрузкой и настраивать проверку наличия мощностей каждые 5 секунд. Аренды Vast.ai и Lambda появились в 1.0.0-beta.40 и проверены по опубликованным API поставщиков на фикстурах (живые запуски аренды не выполнялись). См. [docs/LLM-HOST.md](../LLM-HOST.md).

Новые сессии используют провайдера, которого вы подключили последним, и самую новую модель, доступную этому аккаунту. Модели, к которым у аккаунта нет доступа, пропускаются. Если у этого провайдера нет пригодной модели, Mercury проверяет следующего по времени подключения провайдера. Этот выбор происходит при запуске сессии; сбой запроса в уже существующей сессии остаётся у своего провайдера.

`/model` объясняет выбор. Слово семейства выбирает самую новую модель этого семейства: `/model grok`, `/model deepseek`, `/model kimi` или `/model glm`. Если ни один провайдер не подключён, домашний экран и `/model` направляют к `/logins`. `/defaultprovider` позволяет явно сделать провайдера самым последним выбором.

Доступ к провайдерам по-прежнему зависит от собственных условий провайдера и его доступности. Лицензия Mercury их не заменяет.

## Headless CLI: `mercury run`, Docker и JSON-RPC-раннер

Та же сборка работает без интерактивного интерфейса. `node dist/mercury.mjs --help` перечисляет все флаги.

`mercury run "<prompt>"` запускает prompt без терминального интерфейса:

```sh
mercury run "Summarise this repository." --format text
mercury run "Summarise this repository." --format json
mercury run "Summarise this repository." --format rows
```

- `text` выводит ответ; причина неудачного хода попадает в stderr.
- `json` выводит последнюю строку `outcome` как один JSON-объект.
- `rows` выводит по одному JSON-объекту на строку: сначала `session`, затем `turn` и его строки `text`, `reasoning`, `tool_call`, `tool_result` и `step`, а завершает всё строка `outcome`. Ожидания, прогресс инструментов, фоновые задачи и уведомления имеют собственные строки. Каждая строка содержит `seq`, `timestamp` и `session_id`; строки внутри хода также содержат его номер `turn`. `seq` нумерует поток этого запуска с 1; `turn` считает ходы сессии, поэтому запуск, который продолжает сохранённый разговор (`-c`, `-r`, `--fork`), нумерует свой ход после уже имеющихся в нём ходов, а его строка `session` указывает разговор, который он продолжает, в поле `resume_of`.

Типы строк вывода по их полю `type`:

- `session`: открывающая строка: `version`, `build` (первые двенадцать шестнадцатеричных символов дерева, из которого собран бандл, как их выводит `mercury daemon status`; отсутствует, если рядом с бандлом нет манифеста), `resume_of` (в продолженном запуске — идентификатор сессии разговора, который продолжается; совпадает с `session_id`, если запуск не был создан форком), `cwd`, `model`, `mode`, а также `tools`, `mcp_servers`, `commands`, `agents`, `skills` и `extensions`, которые есть у сессии, и `tools_withheld` (присутствует, когда правило запрета скрывает инструмент по его короткому имени: в каждой записи — `tool`, `rule` и `source`).
- `turn`: ход, который `started` или `waiting`, с его `turn_id`; `model`, `message_ids` и количество `agents`, когда они известны.
- `text`: завершённый текстовый блок: `message_id`, `block`, `text` и его `phase` (`commentary` или `final_answer`).
- `reasoning`: завершённый блок рассуждений: `message_id`, `block`, `text` или `redacted: true`.
- `tool_call`: вызов инструмента: `call_id`, `tool`, `input`, с его `message_id` и `block`.
- `tool_result`: результат вызова: `call_id`, `status` (`ok`, `error`, `aborted` или `refused`) и `output`. Вызов, который модель оформила настолько неверно, что его отклонили до выполнения (неизвестный инструмент, аргументы, которые не являются корректным JSON или не соответствуют схеме инструмента), всё равно получает свою пару: строку `tool_call` с аргументами в том виде, в каком они пришли (`{}`, если они не были объектом), и строку `tool_result` со статусом `refused`, где `output` содержит причину; следом идёт исправляющее `notice`. Такой вызов никогда не запускался и не является отказом.
- `tool_update`: прогресс работающего инструмента: `call_id`, `tick`, `source` (`shell`, `powershell`, `mcp` или `eval`) и те из полей `line`, `elapsed_s`, `lines`, `bytes`, `budget_ms`, `progress` и `total`, которые сообщает вызов. Вызов shell или PowerShell обновляется по мере поступления вывода (команда, которая ничего не выводит, не обновляется), вызов MCP — когда его сервер сообщает о прогрессе, а вызов Eval — пока выполняется его ячейка; никакой другой инструмент не обновляется; вызов Browser или Crewmate не подаёт сигналов до получения результата.
- `step`: один вызов модели главного потока: `message_id`, `model`, `usage` и `stop`, если модель указала, почему остановилась.
- `outcome`: результат хода, описанный ниже.
- `close`: заметка, которую оставляют для следующей сессии при закрытии: `state` (`stored`, `skipped` или `none`), `note_chars` и `usage` вызовов модели, которые её записали, — так что читатель, суммирующий расход всех строк, получит итог из результата хода. Если промпт передан аргументом, заметка запрашивается внутри последнего хода, и `close` предшествует `outcome` этого хода; при `--input rows` строка идёт за последней `outcome`, когда stdin закрывается.
- `wait`: ожидание модели: `state` (`first_byte`, `retry`, `silence`, `loading` или `done`) с показателями, которые несёт это состояние, например `since_ms`, `attempt` и `of`, `delay_ms`, `reason` и `http_status`.
- `heartbeat`: поток модели подал признаки жизни спустя не меньше секунды без разобранного события: поступили байты, которые не дали строки. Строка не содержит ничего другого и появляется не чаще раза в секунду; частота зависит от формы потоковой передачи провайдера, поэтому поток, который никогда не делает пауз между событиями, их не выводит.
- `compaction`: сжатие контекста — `started`, `progress` или `ended`: `trigger` (`manual`, `auto` или `overflow`), `stage`, `fill`, `summary_tokens` и при завершении `exit` (`landed`, `cancelled` или `failed`).
- `mode`: изменился режим разрешений: `mode`.
- `rate_limit`: состояние лимита провайдера: `status` (`allowed`, `warning` или `rejected`), `window`, `resets_at`, `utilization` и поля перерасхода.
- `task`: фоновая задача — `started`, `progress` или `ended`: `task_id`, `task_type`, `description`, `usage`, `summary`, `status` (`completed`, `failed` или `stopped`) и `output_file`, как только они становятся известны.
- `notice`: `warning` или `error` для читателя: `text` и `code`, например `input_refused`.
- `command_output`: вывод слеш-команды, который не дошёл до модели: `command` и `text`.
- `mission_updated`: журнал задач сессии изменился; прочитайте его заново.
- `samples_updated`: образцы сессии изменились; прочитайте их заново.

`--partial` с `--format rows` добавляет строки `block_start`, `text_delta`, `reasoning_delta`, `tool_input_delta` и `retracted`. Дельты относятся к `message_id` и `block`; строка `retracted` отзывает дельты этого сообщения. Завершённая строка текста или инструмента содержит полное значение.

Результат хода содержит `schema`, `turn_id`, `status`, `steps`, `wall_ms`, `usage`, `models` и `denials`, а также `answer` при завершении и `error` (`message`, `class`, необязательный `detail`) при сбое. `stop`, `api_ms`, `cost_usd`, запрошенный вывод `structured` и `notices` включаются, когда они доступны. `wall_ms` — прошедшее время хода. `api_ms` — сумма длительностей каждого запроса к модели, сделанного ходом (включая повторы и запросы crewmates, которые шли параллельно с главным потоком), поэтому он может превышать `wall_ms`, если запросы перекрывались. `cost_usd` — стоимость хода в долларах США по запросам с известной ценой независимо от статуса: запрос, который Mercury не может оценить (в файле нет тарифа, в ответе не указана стоимость), ничего к ней не добавляет и оставляет свою модель в `models` без собственного `cost_usd`; поле отсутствует, только если в ходе ничего не оценено. При входе по подписке Claude запросы Anthropic не имеют цены в долларах, поэтому ни они, ни строка не содержат `cost_usd`; расход при этом сохраняется. В расходе указаны `input_tokens` (включая кэшированные токены), `cached_input_tokens`, `cache_write_input_tokens`, `output_tokens` и, когда они сообщены, `reasoning_output_tokens`; значения суммируются по главному потоку и crewmates. `models` разбивает использование токенов по моделям. `steps` учитывает только вызовы модели главного агента; вызовы модели, сделанные crewmates, появляются как отдельные строки `step` с меткой `parent_call_id`.

Статус — один из следующих: `completed`, `blocked`, `refused`, `failed`, `interrupted`, `turn_limit`, `budget_limit`, `time_limit`, `schema_unmet` или `loop_stopped`. Запуск с `--max-time` (в секундах или `10m`, `1h`) завершается со статусом `time_limit` на следующем шаге, как только истекло время; начатый вызов модели или раунд инструментов не прерываются. Завершённый запуск выходит с кодом 0, прочие исходы — с кодом 1, а ошибка использования — с кодом 2. SIGINT и SIGTERM завершают процесс с кодами 130 и 143 после записи результата прерванного хода. Отклонённый вызов инструмента перечисляется в `denials`. Если отказом был запрос, на который никто не смог ответить (запуск без хоста в режиме, который запрашивает подтверждение, `--mode dontAsk`, или запрос хоста, срок которого истёк), и никакой последующий вызов инструмента в ходе не выполнился успешно, запуск получает статус `blocked`: ответ сохраняется, `error` называет инструмент и способ продолжить (`--allowed-tools`, другой `--mode` или хост, который отвечает на запросы), а запуск завершается с кодом 1. Если последующий вызов инструмента в том же ходе выполняется успешно, ход восстанавливается, завершается статусом `completed` (код 0) и выдаёт предупреждающее `notice` (`"<Tool> was not approved; the run continued with other tools."`). Отказ, на который вы ответили (через правило запрета, хук или хост, который сказал «нет»), оставляет завершённый ход завершённым. Неотвеченный вызов `AskUserQuestion` тоже завершает запуск статусом `blocked`, а вопрос цитируется в `error`. Mercury определяет исход по записанным запросам запуска, а не по тексту ответа, поэтому вопрос, который есть только в ответе, оставляет ход со статусом `completed`. Неизвестная слеш-команда получает статус `refused` с той же фразой, что выводит интерактивный экран (`Unknown command: /name · /help lists commands`), и завершается с кодом 1.

`--input rows` требует `--format rows` и читает по одному входному объекту в строке:

```sh
printf '%s\n' '{"type":"prompt","content":"Summarise this repository."}' | mercury run --input rows --format rows
```

Типы входных данных: `prompt` с `content` (текст или блоки text/image), `shell` с `command` и `note` с `to` (идентификатор агента) и `content`. Каждый принимает необязательный `id`; строки prompt и shell также принимают `priority` (`now`, `next` или `later`), `sent_at` и `origin`. Отклонённая форма входных данных порождает `notice` с кодом `input_refused`; некорректный JSON завершает запуск. Эти строки несут только входные данные; ответы на запросы разрешений передаются по протоколу раннера, описанному ниже.

Используйте `mercury run -` или передайте текст в `mercury run` через конвейер, чтобы прочитать весь промпт из stdin. Рядом с аргументом-промптом переданный текст добавляется как отделённый контекст: конвейер читается до закрытия или до того, как он молчит в течение одной секунды, поэтому поток, который продолжает поступать, читается до конца, а конвейер, который остаётся открытым и молчит, не задерживает запуск. Без промпта и при терминале в stdin `run` выводит справку по использованию и завершается с кодом 2.

`--mode <mode>` выбирает режим разрешений. `--sovereign` запускает без запросов разрешений, а `--allow-sovereign` делает этот режим доступным для последующего переключения. Политика разрешений и правила запрета по-прежнему действуют. Пользователь root, переходящий в режим sovereign, получает одно уведомление в stderr; запуск продолжается.

Используйте `-c`, чтобы продолжить последний разговор, `-r`, чтобы возобновить по ID, заголовку или через выбор, `-w`, чтобы запустить в управляемом worktree, и `--lean`, чтобы получить минимальную сессию. У `run` нет хоста, который отвечал бы на запросы разрешений: его правила разрешений и режим определяют, что может выполняться, а вызов, которому нужно подтверждение, отклоняется.

### Headless-образ

`Dockerfile` в корне репозитория собирает образ Linux x64 для CI и серверов. Его точка входа — `mercury`, а команда по умолчанию — `run`, поэтому образ выполняет один промпт над смонтированным деревом и завершается с кодом этого запуска:

```sh
docker build -t mercury .
docker run --rm -e ANTHROPIC_API_KEY="$ANTHROPIC_API_KEY" -v "$PWD":/work mercury run "Summarise this repository." --format text
docker run --rm mercury --version
```

В образе находятся бандл, среда Node 24 runtime (в `PATH`), вендорные инструменты поиска, shell, отладчика, языковые и графические инструменты, `git` и хранилище сертификатов; нет начального экрана и процедуры входа. Образ работает от непривилегированного пользователя `mercury`, а его каталог конфигурации находится внутри контейнера (`MERCURY_CONFIG_DIR`); `/work` — рабочий каталог. Цвет и мышь определяются собственным распознаванием терминала, а `--user 0` запускает процесс от root с тем самым уведомлением sovereign, что описано выше.

Ключ провайдера передаётся переменной окружения, в тех же написаниях, которые продукт читает везде: `ANTHROPIC_API_KEY` или `ANTHROPIC_AUTH_TOKEN`, `OPENAI_API_KEY`, `GEMINI_API_KEY` или `GOOGLE_API_KEY`, `XAI_API_KEY` (и `XAI_MANAGEMENT_API_KEY` для его счётчика использования), `DEEPSEEK_API_KEY`, `MOONSHOT_API_KEY`, `ZAI_API_KEY`, `OPENROUTER_API_KEY`, `HF_TOKEN`, `MISTRAL_API_KEY` (и `MISTRAL_ADMIN_API_KEY` для счётчика организации), `NOUS_API_KEY`, `OPENCODE_API_KEY`, `MINIMAX_API_KEY`, `TOGETHER_API_KEY` или `TOGETHER_AI_API_KEY`, `COHERE_API_KEY` или `CO_API_KEY`, `GROQ_API_KEY`, `CEREBRAS_API_KEY`, `FIREWORKS_API_KEY`, `DASHSCOPE_API_KEY`, `MODEL_API_KEY` или `META_API_KEY`, `MERCURY_COMPAT_API_KEY` для пользовательской конечной точки, совместимой с OpenAI, и `MERCURY_LOCAL_API_KEY` для локального сервера. Без ключа запуск отказывает одной строкой и завершается с кодом 1. `docker run -i … mercury run -` читает промпт из stdin.

### Размещение сессии

`mercury runner` обслуживает сессию для хоста через stdio: JSON-RPC 2.0, одно сообщение в строке. Хост первым отправляет `initialize` и ждёт ответа, прежде чем передавать работу:

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocol":1,"host":{"name":"my-host","version":"1.0.0"},"capabilities":{"holds_asks":true,"elicitation":false,"partial_rows":false}}}
```

Имя и версия хоста передаются в `host`; `capabilities` объявляет `holds_asks`, `elicitation` и `partial_rows`. Каждый `id` запроса — положительное целое число: запрос с любым другим `id` получает ответ `-32600` с `id: null`, поэтому нумеруйте запросы с 1.

`queue/add` принимает тот же объект промпта, shell или note, что и входные строки выше. Вывод приходит в уведомлениях `row`. `session/facts` читает состояние сессии; `session/set_mode` меняет режим разрешений сразу; `session/set_model` и `session/set_effort` меняют модель и уровень effort, а изменение, сделанное во время хода, удерживается до его окончания: ответ содержит `at: "turn_end"`, затем `session/applied` сообщает о нём. `turn/interrupt` останавливает ход; закройте stdin, чтобы завершить сессию.

Запросы разрешений приходят как `permission/request` с `kind: "tool"` или `kind: "network"`. Хост отвечает `outcome: "allow"` или `outcome: "deny"`; ответ allow может нести изменённые `input` и правила `rules`. Отозванный запрос отправляет `$/cancel_request` с его `request_id`. `holds_asks` передаёт хосту владение таймером запроса. Вопрос MCP использует `elicitation/request` только тогда, когда хост объявляет `elicitation`; иначе на него отвечают `cancel`.

На неизвестный метод отвечают `-32601`, на неверные параметры — `-32602`, на `id`, который не является положительным целым, — `-32600`, а на запрос до инициализации — `-32002`. Отказ по правилу — `-32010`: фраза в `error.message`, причина в `error.data.kind`, например `mode`, `model`, `effort` или `claim`. Раннер отвечает на некорректную строку `-32700` и продолжает работу; три некорректные строки подряд его завершают.

### Другие команды

Доступные команды включают:

- **`mercury health`**: диагностический отчёт, он же сертификат состояния. `--json` возвращает полный отчёт, `--deep` запускает глубокую инвентаризацию, а `--fix` выполняет направляемые исправления.
- **`mercury auth login [<family>]|list|status [<family>]|logout [<family>]|mint`**: вход (`login [<family>]`), список семейств провайдеров (`list`), проверка, выполнен ли вход в аккаунт (`status [<family>]`), выход (`logout [<family>]`) или выпуск долгоживущего токена Anthropic (`mint`).
- **`mercury models [--json]`**: выводит модели, доступные вошедшим аккаунтам (те же сведения, что `mercury://models`).
- **`mercury mcp`**: управление серверами MCP с помощью `add`, `import`, `list`, `get`, `remove`, `trust-reset` и `serve`.
- **`mercury extensions`**: установка расширений и управление их источниками. Действия: `list`, `sources`, `add`, `remove`, `refresh`, `install`, `trust`, `enable`, `disable`, `update`, `uninstall`, `fence`, `unfence`, `inspect` и `scaffold`.
- **`mercury roster`**: выводит инвентарь агентов.
- **`mercury usage`**: выводит компактную строку с показателями, которую показывает экран `/usage`; `--json` выводит всё показание целиком: окна каждого вошедшего провайдера с использованием и временем сброса, показатели и кредиты, которые он указал, каждый с источником и давностью, а также расход сессии по моделям, считанный так же, как его считывает экран (считыватель каждого вошедшего провайдера опрашивается один раз, как при открытии).
- **`mercury daemon run|status|stop|restart`**: запускает, проверяет, останавливает или перезапускает фоновый демон. Его слоты сессий — это дочерние процессы `mercury runner`; демон отправляет им промпты и обслуживает их запросы разрешений.
- **`mercury sessions list`** (также просто `mercury sessions`): выводит сохранённые сессии этого проекта, от новых к старым: идентификатор, время последней записи, размер, `live`, когда демон сейчас обслуживает сессию, а также её заголовок или первый промпт; `--all` читает все проекты, `--limit <n>` ограничивает список. Идентификатор — то, что повторно открывает `mercury --resume <id>`, и то, что удаляет `sessions delete`.
- **`mercury sessions delete <id>`**: намеренно удаляет одну сохранённую сессию — её транскрипт и записи, которые хранятся рядом (квитанции, снимок для возобновления), — после вопроса-подтверждения; `--yes` пропускает вопрос в скриптах. Сессия, которую демон обслуживает сейчас, отклоняется, а на неизвестный идентификатор выводится подсказка на список (`/sessions` внутри Mercury). Сохранённые сессии иначе никогда не удаляются сами по себе.
- **`mercury host [status|start|stop|restart|logs|uninstall|add|recipes]`**: запускает локальный или SSH-компьютер как сервер моделей для всех сессий, использующих общий каталог конфигурации (`compat/box-<name>/<model>`), с проверенным локальным хранилищем весов или подтверждённой загрузкой. См. [docs/LLM-HOST.md](../LLM-HOST.md).
- **`mercury lsp list`** и **`mercury lsp install <server>`**: каталог языковых серверов, где каждый сервер либо установлен (с бинарным файлом), либо отсутствует (с указанием способа установки); `install` показывает способ установки сервера, запрашивает подтверждение, выполняет ровно его (`--yes` пропускает вопрос в скриптах) и сообщает, куда попал бинарный файл. Неизвестный сервер отклоняется с выводом списка. Mercury никогда не устанавливает языковой сервер самостоятельно; открытие файла запускает только уже установленный сервер.
- **`mercury acp`**: обслуживает редактор по Agent Client Protocol, с дочерним процессом runner для каждой сессии. `mercury bridge install` устанавливает расширение VS Code; `mercury bridge status` проверяет его; `mercury bridge uninstall` удаляет его.
- **`mercury godot run|check|capture|frames|profile|tour|jobs|cancel|result`**: управляет заданиями движка для проекта Godot в текущем каталоге. Mercury запускает наборы тестов на собственных headless-воркерах из замороженной копии проекта. Сервис включает шлюз компиляции, захваты, статистику кадров, завершённые профили, доступ к очереди заданий, отмену и результаты по ID. См. [docs/VULCAN-GODOT-TOOLS.md](../VULCAN-GODOT-TOOLS.md).
- **`mercury image <image>`**: выводит изображение в терминал.
- **`mercury install`** и **`mercury update`** (псевдоним `upgrade`): установка или обновление архивов релизов; с `--json` документ выводится в stdout независимо от вердикта, а код выхода показывает, завершилась ли команда с ошибкой. См. [Установка](#установка).
- **`mercury version`** и **`mercury help [command]`**: выводят строку версии или страницу справки, то же, что `--version` и `--help`; ни одна из команд не запускает сессию.

## Что внутри: память Mneme RAG, LSP, AST для 23 языков, отладчик DAP, веб-поиск и мосты

- **Гибридная RAG-память проекта Mneme.** Mneme включена по умолчанию и хранит факты каждого проекта в простых markdown-страницах по темам (`Retain`, `Recall`, `Reflect`, `Correct`). Recall объединяет работающую на устройстве семантическую модель эмбеддингов BGE на 118 МБ (`bge-base-en-v1.5` `q8_0`, MIT, входит в каждый архив релиза, собрана под его платформу; см. [Дополнительные компоненты](#дополнительные-компоненты)) с ранжированием слов BM25 со стеммингом, весом по давности и отслеживанием цитат через reciprocal rank fusion (`k = 60`). Закреплённые правила (`pin: true`) загружаются дословно на закреплённую полку и меняются только по вашему слову. При старте сессии Mercury оценивает незакреплённые факты и прежние заметки по текущей ветке, недавно затронутым файлам и заметке о передаче последней сессии в отдельном лимите запуска (`memory.startLimit`, по умолчанию 4 000 символов). Проверки противоречий при записи перехватывают смену полярности, отрицание и смену чисел до того, как сохраняется конфликтующий факт. При выходе каждая сессия записывает своими словами заметку о передаче на страницу входа следующей сессии, а также необязательную запись в журнале сессии. `/memory` открывает центр памяти, а `/memory page` выводит библиотеку в браузере в виде графа с узлами и рёбрами. См. [docs/MNEME.md](../MNEME.md).
- **LSP-анализ кода, переписывание AST для 23 языков, отладчик DAP и ячейки `Eval`.** Чтения с якорями и атомарные правки нескольких файлов (`ChangeSet`); запросы к языковому серверу (`LspRead`) и рефакторинги с предпросмотром перед применением (`LspRename`, `LspMoveSymbol`, `LspMoveFile`, `LspCodeAction`, `LspFormat`); поиск по синтаксическому дереву и переписывание (`AstSearch`, `AstEdit`) с метапеременными `$NAME` и `$$$NAME` по 23 грамматикам в архивах релизов (16 в каждой сборке `bun install` и 7 в пакете грамматик); постоянные ячейки кода на Python (`python3`) и JavaScript (ES-модуль Node) (`Eval`); а также отладчик по Debug Adapter Protocol (`Debug`), работающий через `debugpy`, `js-debug`, `lldb`, `gdb`, `dlv`, `netcoredbg`, `rdbg`, адаптер отладки Dart SDK, `kotlin-debug-adapter`, адаптер отладки elixir-ls и Godot. В инструменте `Test` операция `debug` пошагово вводит падающий тест на Python (`pytest`, `unittest`), JavaScript/TypeScript (`node-test`, `vitest`, `jest`), Go (`go test`) или Rust (`cargo test`) прямо в сессию `Debug`. См. [docs/LANGUAGE-SERVICE.md](../LANGUAGE-SERVICE.md), [транзакции изменений](../CHANGE-TRANSACTIONS.md), [структурные шаблоны](../STRUCTURAL-PATTERNS.md), [ячейки кода](../EVAL.md) и [отладчик](../DEBUGGER.md).
- **`WebSearch` без ключей и `WebFetch` в markdown.** `WebSearch` проходит по одной цепочке источников: сначала собственный поиск провайдера в реальном времени, если модель сессии его поддерживает (`ProviderSearch`), затем сохранённые ключи Brave или Tavily, затем официальные API, которые выбираются по виду запроса (Stack Exchange, npm, PyPI, crates.io, поиск по коду GitHub, Hacker News Algolia, Wikipedia), затем настроенные JSON-API SearXNG (`MERCURY_SEARCH_SEARXNG_INSTANCES`) и, наконец, извлечение страниц DuckDuckGo без ключа (включено по умолчанию; выключается в `/config` или через `MERCURY_SEARCH_KEYLESS=0`). Каждый ответ остаётся в пределах 2 000 токенов и называет ответивший источник. `WebFetch` читает публичные страницы как markdown, сохраняя их собственные слова, в пределах бюджета вызова 38 000 символов (страница, которой нужен браузер, читается через размещённый читатель `r.jina.ai`, если только не задано `MERCURY_FETCH_READER=0`; адрес внутренней сети в него никогда не отправляется). См. [docs/ENGINES.md](../ENGINES.md).
- **Агенты, crewmates от разных провайдеров (`Crewmate`), worktrees и аренды файлов.** Два встроенных агента (`mercury-crew` для делегированной работы любого вида и `mercury-scout` для разведки только на чтение) работают наряду с определениями агентов, которые вы создаёте в `/agents`. Запускайте crewmates на любом провайдере, в который вы вошли, изолируйте параллельную работу в рабочих копиях `git worktree` (`isolation: "worktree"`), согласовывайте общие файлы через аренды файлов проекта внутри процесса (`mcp__mercury__lease_take`, `mcp__mercury__lease_release`, `mcp__mercury__lease_list`), а направлять или возобновлять crewmates по имени или идентификатору можно через `SendMessage` и `ResumeCrewmate`. Следите за crewmates и запусками рабочих процессов в `/crewmates` и `/runs`. См. [docs/CREW.md](../CREW.md).
- **Управление компьютером на рабочем столе.** Включается по умолчанию, когда доступен нативный драйвер рабочего стола. Инструмент `Computer` делает снимки экрана и управляет мышью и клавиатурой в приложении переднего плана. Mercury проверяет приложение по имени и идентичности перед действием и запрашивает одобрение, если только ваши правила разрешений, предоставление сессии, настройка доступа или режим разрешений уже не разрешают действие; останавливается по `Esc`; позволяет управлять рабочим столом только одной сессии за раз и не сохраняет снимки экрана в файле сохранённого разговора. Чтобы убрать инструмент, задайте `MERCURY_COMPUTER_USE=0`. См. [docs/COMPUTER-USE.md](../COMPUTER-USE.md).
- **Голосовой ввод Whisper на устройстве (`/voice`).** `/voice on` загружает английскую речевую модель на 60 МБ (`base.en-q5_1`) при первом использовании, проверяет её контрольную сумму SHA-256 и включает диктовку; `/voice off` выключает её. Удерживайте пробел 1 с, чтобы говорить, и отпустите, чтобы остановить запись, или выполните просто `/voice`, чтобы начать и остановить запись, пока голос включён. Whisper расшифровывает речь на устройстве, поэтому звук голоса никогда не покидает машину; `MERCURY_WHISPER_MODEL` выбирает `tiny.en-q5_1`, `small.en-q5_1`, многоязычную `base-q5_1` или локальный файл `.gguf`. См. [docs/VOICE.md](../VOICE.md).
- **Планировщик cron и сессий Saturn (`/saturn`).** Запланируйте промпт для существующей сессии (`CronCreate`, `CronList`, `CronDelete`, `ScheduleWakeup`, `/loop`) или запланируйте новую сессию на заданное время. Расписания могут выполняться один раз или повторяться. См. [docs/SATURN.md](../SATURN.md).
- **Мосты к VS Code (ACP), Unity, Blender, Godot и Aseprite.** `mercury acp` подключается к редакторам, которые поддерживают Agent Client Protocol. Расширение VS Code (`mercury bridge install`) запускает Mercury в редакторе по этому протоколу: чат, сессии, агенты, артефакты и ревью, при этом выделение в редакторе и диагностика передаются с каждым промптом. Отдельные интеграции, включаемые по желанию, подключаются к запущенным редакторам Unity (`MERCURY_UNITY=1`), Blender (`MERCURY_BLENDER=1`) и Godot (`MERCURY_GODOT_TOOLS=1`), а также дают пакетный доступ к Aseprite (`MERCURY_ASEPRITE=1`). См. [Unity](../UNITY-BRIDGE.md), [Blender](../BLENDER-BRIDGE.md), [Godot](../VULCAN-GODOT-TOOLS.md) и [Aseprite](../ASEPRITE-BRIDGE.md).
- **Расширения.** У каждого расширения один манифест. Источники добавляются из URL git, локальной папки или архива и утверждаются по хешу их contributions. См. [docs/EXTENSIONS.md](../EXTENSIONS.md).
- **MCPs & Skills.** Настройка для каждого репозитория: что загружают сессии, с именованными пресетами и элементами управления, которые можно менять во время сессии. См. [docs/KIT.md](../KIT.md).
- **Диагностика.** Проверка состояния и `/health` формируют отчёт, опирающийся на данные диагностики, с вердиктом `certified`, `caution` или `fault` и проверенными исправлениями. См. [docs/HEALTH-CERTIFICATE.md](../HEALTH-CERTIFICATE.md).
- **Доверие и разрешения.** Доверие к рабочему пространству, правила и режимы разрешений, а также команды, которые каждая сессия отклоняет. См. [docs/TRUST.md](../TRUST.md).
- **Apollo Mode**, интервью по спецификации: ответьте на вопросы агента, чтобы завершить спецификацию, по которой он создаст прототип. См. [docs/APOLLO-MODE.md](../APOLLO-MODE.md).
- **Восстановление.** Атомарная публикация, журналируемые операции и сверка при запуске. См. [docs/DURABILITY.md](../DURABILITY.md).

Флаги выполнения определены в `src/substrate/flagRegistry.ts`, доступны как настройки `MERCURY_*` и выводятся по запросу. Совместимость интеграций описана в [docs/COMPATIBILITY.md](../COMPATIBILITY.md). Полный указатель документации — [docs/README.md](../README.md).

`/mouse off` возвращает указатель терминалу для нативного выделения и копирования текста. Настройка сохраняется и отображается в `/config` как Mouse capture.

В строке использования (usage) навыка обязательный аргумент начинается с `<…>`. Например, `/update-config` и `/debug` требуют аргумент. Отправьте такую команду без аргумента, и вы получите её описание и строку использования; ход не начинается. Если выбрать её в автодополнении и нажать Enter, в поле останется `/name `, куда можно добавить аргумент. `/loop` не требует аргумента и выполняется сразу.

## Сообщение о проблеме

Для короткого отчёта используйте [форму для тестировщиков](https://mercury-cli.ai/report) или `/bug --short <what you tried>` внутри Mercury. Форма запрашивает вашу ОС, что вы пробовали и что сломалось; дамп проверки состояния не нужен.

Выполните `/bug <what happened>` внутри Mercury, чтобы просмотреть отчёт перед отправкой через вошедший в аккаунт GitHub CLI (`gh`). Без `gh` Mercury сохраняет локальный черновик в каталоге конфигурации и указывает страницу issues репозитория.

Вы также можете открыть задачу напрямую по шаблону bug, provider/model или feature request. Укажите вывод `--version`, ОС, терминал и точные шаги. Отчётам об ошибках и о провайдерах также нужен вывод `mercury health --json` или `node dist/mercury.mjs health --json` для сборки из исходников. Текстовая копия экрана с ошибкой тоже полезна.

Сообщайте о проблемах безопасности приватно через вкладку Security репозитория. Не публикуйте их в открытых issues. См. [SECURITY.md](../../SECURITY.md). [CONTRIBUTING.md](../../CONTRIBUTING.md) описывает issues, пул-реквесты и проверки.
