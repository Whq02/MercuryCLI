# Extensions

An **extension** is a folder with ONE manifest, `mercury-extension.json`, that names it,
versions it, says what it adds to Mercury and what it needs from the machine. Everything
else in the folder is content the manifest points at — Mercury reads nothing that is not
declared. Extensions come from **sources** the operator adds: a git repository on any
host, a local folder, or an archive. Mercury ships with no source and never adds one on
its own.

This page is for makers: how to write an extension, publish a source, and what the
operator sees on the other side. The board itself is `/extensions` (two sections,
installed and sources); the headless verbs are `mercury extensions <verb>`.

## What an extension is

```
review-tools/
├── mercury-extension.json        the one manifest (required; the folder's root)
├── README.md                     for humans (recommended)
├── skills/
│   ├── review/SKILL.md           one skill = one folder with SKILL.md
│   └── summarise/SKILL.md
├── commands/
│   └── changelog.md              one command = one markdown prompt file
├── agents/
│   └── reviewer.md               one agent = one markdown definition
└── server/
    └── index.mjs                 whatever the extension's own servers need
```

Every contribution kind mirrors what the operator can already place by hand in their own
`.mercury/` estate, with the same shapes — a maker learns one vocabulary and nothing is
reserved to built-ins:

- **skills** — directories whose child folders each hold a `SKILL.md`; registered as
  `/<name>:<skill>`, user-invocable and model-invocable per the skill's own frontmatter.
- **commands** — directories of `<cmd>.md` prompt files (one level deep; a subdirectory
  namespaces `/<name>:<dir>:<cmd>`).
- **agents** — directories of `<agent>.md`; registered as agent type `<name>:<agent>`.
  Privilege-raising frontmatter (`permissionMode`, `hooks`, `mcpServers`) is ignored with
  a health note: an extension agent runs under the session's mode, always.
- **hooks** — the operator's own hooks shape: event → matchers → command hooks. Only
  command hooks; each is time-bounded, its output is bounded, and a failing hook is
  logged and counted, never fatal to the session.
- **servers** — MCP servers (`stdio`, `http`, or `sse`), connected as
  `ext:<name>:<server>`; their tools reach the model like any MCP tool and pass the
  permission engine like any MCP tool.
- **language** — language servers in Mercury's own config shape, started as
  `ext:<name>:<server>`.
- **channels** — which of the extension's own servers may post channel messages into the
  session once approved; an undeclared server's posts are dropped with a health note.
- **keybindings** — default chords for the extension's OWN commands and skills, applied
  only when the operator's keybindings leave the chord free.

The `needs` block declares binaries, env vars, network hosts (informative, painted on the
approval card) and operator-configured `options`. A `sensitive` option lives in the
secure store, never a settings file; it renders as a visible placeholder in any prose the
model reads and arrives for real only in hook and server environments.

## The contract (generated from the runtime schemas)

- an extension's name: lowercase letters, digits and hyphens, 1–40 characters, starting with a letter or digit; the id everywhere is `<name>@<source label>`; the reserved labels are `project`, `session`, `mercury`.
- ONE manifest, `mercury-extension.json`, at the extension root; every path in it stays inside the root.
- ONE catalogue, `mercury-extensions.json`, at a source root — or a single `mercury-extension.json` when the repository IS the extension.
- unknown top-level keys: a warning at load, an error under `mercury extensions validate`; unknown keys INSIDE `contributes`/`needs` are errors at load.
- `module` is reserved: this build loads declarative extensions; `module` is reserved.
- approval is per contributions hash — sha256 over the canonicalised `contributes` + `needs` blocks: a version bump alone carries approval over; a changed command line, server, or need re-asks.
- the substitutions: `${MERCURY_EXTENSION_ROOT}`, `${MERCURY_EXTENSION_DATA}`, `${option.KEY}` in command lines, args, env values and prompt bodies; every other `${…}` stays literal. Hooks and servers receive `MERCURY_EXTENSION_ROOT`, `MERCURY_EXTENSION_DATA` and one `MERCURY_EXTENSION_OPTION_<KEY>` per option; a `sensitive` option renders a visible placeholder in prose the model reads.

## The maker's loop

1. `mercury extensions init review-tools` scaffolds the folder (manifest with the
   required fields, an empty `skills/`, a README) — or write it by hand from this page.
2. Put it in the project: `.mercury/extensions/review-tools/`. Open Mercury there.
   `/extensions` shows `◇ found`. Press `i`: the approval card — what it will run on
   your machine, what it adds to the model's reach, what it needs. Approve.
3. Edit a skill; press `r` (or `/extensions reload`): the change is live. If the
   manifest's contributions changed, the row reads `changed — re-approve` and the card
   shows the diff.
4. `mercury extensions validate .mercury/extensions/review-tools` lints everything the
   runtime tolerates (unknown top-level keys, side files the runtime ignores, a hook
   whose script is missing).
5. Publish: push the folder as its own repository — a single-extension source — or add
   it to a catalogue. Others add the URL.

## Publishing a source

A source root carries ONE of:

- `mercury-extensions.json` — a catalogue listing extensions (a multi-extension source), or
- `mercury-extension.json` — a single extension; the repository IS the source.

A catalogue entry names the extension, the version at that ref, one line of description,
and exactly one of `path` (inside this source) or `git` (+ optional `ref`) for an entry
hosted in another repository. A catalogue whose `name`/`version` disagree with the
fetched manifest is a lying catalogue: the install refuses and says so.

Ship a `README.md` from the template (`docs/templates/extension-source-README.md`, also
written by `mercury extensions init --source`): what the source offers, how to add it,
what each extension needs, who maintains it, the licence.

## What the operator sees

- `mercury extensions add <url|path|archive>` (or `a` on the sources tab) — classify,
  blocklist check, fetch, validate, label, record. Adding never installs.
- `i` / `mercury extensions install <name>[@label]` — fetch the copy, then the approval
  card over the REAL manifest. `--yes` is the only scripted approval. Approval is per
  exact contributions hash: a version bump that changes nothing carries approval over;
  an update that adds a hook shows the diff and asks again.
- `space`/`enable`/`disable` — the switch, everywhere or per project; `b` blocks;
  `x`/`uninstall` removes everything (files, records, switches, options, secrets, data —
  or keeps the data on request). Per repository, the Boot face's MCPs & Skills
  menu adds a second switch: an extension's master row there turns its
  contributions off for sessions born in that repository, and a session is
  served an extension only when both switches agree ([KIT.md](KIT.md)).
- `u`/`check` refreshes a source — the only act that discovers a newer version;
  `U`/`update` applies one; the previous version is kept until the first clean load and
  `--previous` swaps back.
- Health lives on the row, always with the reason: `● on` · `◑ partial · server x: node
  not on PATH` · `✕ broken · manifest invalid: contributes.hooks[0]`. `/health` carries
  one `extensions` row.

## The verbs

| verb | does |
|---|---|
| `list [--json] [--source <label>]` | the installed roster with state + first reason; or a source's offer |
| `sources [--json]` | the sources with state |
| `add <url\|path\|archive> [--label <l>]` | add a source (installs nothing) |
| `remove <label> [--and-extensions]` | remove a source; its copies keep working |
| `check [<label>]` | refresh one or every source; prints the updates found |
| `install <name>[@label] [--yes] [--project]` | fetch + the card + the switch |
| `approve <id> [--yes] [--project]` | the card for an installed-off or found extension |
| `enable <id> [--project]` / `disable <id> [--project]` | the switch |
| `update <id>\|--all [--yes]` / `update <id> --previous` | apply a known update / swap back |
| `uninstall <id> [--keep-data]` | remove with no residue |
| `block <id\|label\|url>` / `unblock …` | the blocklist |
| `validate <path>` | the maker's linter |
| `init <name> [--source]` | scaffold an extension or a source root |
